# 项目复盘与发布检查

根据用户实际提供的变更、日志、截图说明、测试结果和决策记录，形成可供行动的项目状态判断。本技能是文本分析与文档整理，不会自行运行测试、检查设备、部署、发布或联系他人。

## 先固定要判断的对象

识别项目、版本、分支或提交、环境和这次目标；保留用户已经给出的边界。多个工作区、开发实例、安装版、服务器、设备或数据集分别记录，不把一个对象的证据转移到另一个对象上。标识缺失时注明，避免把不同时间的记录拼成同一次验收。

用户要进度摘要时优先回答完成了什么、还有什么阻碍下一步；用户要复盘时解释结果与原因；用户要发布检查时围绕目标使用场景和验收条件组织证据。不要自动升级为安全审计、重构计划或无边界的检查清单。

## 把行为与证据连接起来

对会影响决策的重要结论，说明预期行为、实际观察、对应环境和证据位置。可按需要使用简表，但不要求每个小改动都填完整模板。

区分以下层次：

- 有实现或配置：能从给定变更或配置看到意图。
- 已验证：提供了针对相关行为的检查结果，且版本与环境可对应。
- 已部署或已安装：目标环境确实完成更新。
- 已完成目标环境验收：在目标运行条件下观察到预期行为。

构建成功不自动证明 GUI 可用；模拟服务或协议测试不自动证明真实设备可用；开发实例通过不自动证明安装版通过；配置启用不自动证明连接成功。用准确的层次描述已知结果，不要求与当前变更无关的额外验收。

## 阅读测试和故障记录

保留测试范围、通过与失败数、执行环境、失败触发条件，以及影响结论的跳过项。没有结果表示未知，不表示通过或零失败。重复同一组测试不能简单累加成更多独立场景。

区分已证实的问题、待验证的解释和建议尝试的修复。失败存在于变更之前需要有前后证据支持；只有当前失败日志时，不直接称为“历史问题”。有重试成功时，说明重试是否改了代码、数据、环境或时序，并判断最初的问题是否已被解释。

## 给出合适的下一步

优先选择能消除关键不确定性的最小检查。例如重现某个失败场景、在目标安装版验证一条用户流程、核对更新后的版本标识，或确认备份能够恢复。根据影响、发生条件、可恢复性和证据强弱排序，不只按问题数量排序。

发布建议与证据匹配：可以建议继续开发、进入有限试用、等待某个阻断项，或按用户已定义标准发布。若用户没有提供正式发布标准，说明本次判断依据和仍需负责人决定的事项，不自创“全部通过”的正式认证。

## 交付文本

开头给出当前状态和判断依据，再写关键完成项、未解决的问题及下一步。交接时保留必要的版本、路径、链接、复现条件和责任归属；不复制无关日志或私人凭据。面向评审或发布的文档描述最终变化及验证范围，省略不会影响判断的尝试过程。

对保留用户数据、设置、凭据或兼容性的声称，需要相应证据；没有执行恢复、迁移或留存检查时，标为待确认。结尾让读者能明确知道下一步做什么，以及完成后应观察到什么结果。
