# 标注法杖施工与 Mod 内机器人身体

状态：2026 年 11 月 20 日确定由现有 Mineflayer Core 执行 M3 施工。Mod 身体实验仍保留为独立候选。

## 目标

玩家在 Minecraft 里明确告诉 DeskPet「在哪里、建什么、允许动哪些方块」。玩家用法杖圈地、看预览、点确认之后，机器人自己整地和施工，不靠模型猜坐标。

机器人前期自主发育；玩家做出法杖（需要钻石，属于中期）后，可以用它指挥机器人干活。做出法杖之前，照样可以用游戏聊天下命令。

## 已定的产品决定

| 项 | 决定 |
|---|---|
| 游戏版本 | Java 1.21.8（与现有 Mineflayer Core 一致） |
| Mod | Fabric 服务端 Mod，用 Polymer 显示自定义物品、sgui 做菜单，玩家用原版客户端即可进服 |
| 运行方式 | DeskPet 启动本地 Fabric 专用服作为「机器人的世界」，玩家从「多人游戏」加 `localhost` 进入 |
| 玩家下线时 | 世界继续运行，机器人继续自主发育 |
| 多人 | 先单人；以后朋友加入时开白名单和正版验证 |
| 机器人身体 | 先做和身体无关的公共部分，同时做 Mod 内身体实验；按实验结果决定施工由谁执行，再逐项迁移 |
| 授权 | 游戏内菜单的「确认开工」按钮可以替代桌面审批，按计划逐份授权；DeskPet 里有开关，默认关 |
| 模型 | 不参与圈地施工链路。圈地施工任务只能来自 Mod 发出的授权，模型工具和聊天文字都不能创建或批准这类任务 |
| 跨界的树 | 默认判冲突。玩家可以扩大选区，或勾选「只砍框内（接受框外树叶自然凋落）」 |
| 材料 | 首版玩家备料，再加上整地挖出来的土石；不自动外出采集 |
| 法杖配方 | 两根木棍、一个紫水晶碎片、一个钻石，按下面的形状斜放 |

```
·     紫水晶  钻石
·     木棍    ·
木棍  ·       ·
```

## 为什么考虑把机器人身体搬进 Mod

好处：

- 方块、背包和实体都直接读服务端，没有协议解析和同步问题。现在背包只在关闭界面时同步，见 `core/README.md` 规则 3。
- 门、楼梯、床这类有朝向的方块可以稳定放成指定状态，结果在服务端直接校验。
- 「框外不动」在服务端强制执行。
- 机器人不需要游戏账号，服务器可以开正版验证。Mineflayer 机器人目前只能进离线模式的服务器。
- 动作和服务器刻同步执行，没有子进程卡住、stdin 读不到这类问题。

代价：

- `electron/minecraft-companion-runtime/core` 约 2.15 万行，大约 2000 处直接调用 Mineflayer 接口（`bot.entity`、`bot.blockAt`、`bot.inventory`、`bot.pathfinder` 等）。逃跑、战斗、护卫、从零建家、种田、下界、末地都是一轮轮实测调出来的，不能一次性重写。
- Java 寻路要自己写；Baritone 依赖客户端，不能直接用在服务端假玩家上。
- 选址、调度这类逻辑 bug 不是 Mineflayer 造成的，换身体之后也得重新验证。

结论：先做两种身体都需要的部分，同时用实验验证 Mod 身体，再按能力逐项迁移。迁移完成之前，Mineflayer 版继续保留，用于原版服务器和别人的服务器。同一个世界里同一时间只有一个机器人身体。

## 总体结构

| 部分 | 负责 |
|---|---|
| **Fabric Mod**（`minecraft-mod/`，权威方） | 法杖与配方、圈地与撤销、菜单、计划编译、预览、冲突与材料清单、确认、计划状态机、服务端拦截、进度显示、最终验收比对；实验通过后再加上机器人身体（假玩家、寻路、动作、施工执行） |
| **Mineflayer Core**（现有） | 过渡期的自主发育；实验不通过时也负责执行施工 |
| **DeskPet 主程序** | 启动和管理专用服、模型、任务决策、审批开关、审计记录、运行状态页；只在 Mod 判定完成后才说「完成」 |

DeskPet 和 Core 之间现有的任务协议（`core-host.js` / `protocol.js`：任务 ID、开始、取消、暂停、查询、策略，以及 `goal_set`、`goal_done`、`goal_failed`、`player_chat` 事件）保持不变。换成 Mod 身体时，加一个同样协议的转接层，主程序不用关心背后是哪种身体。

## 法杖与圈地

- 物品是 `deskpet:survey_wand`：服务端真实注册、有真实配方，经 Polymer 显示给客户端。
- 右键方块：依次设置角 1、角 2。
- 潜行加右键空气：撤销上一个角。
- 潜行加右键箱子：设为材料箱。材料箱可以在框外，机器人只开箱，不改动方块。
- 两个角都设好后，右键空气打开菜单。
- 两个角只决定水平范围。垂直范围由计划算出来，并在预览里标明。首版选区水平最大 48×48。
- 圈地、打开菜单、预览都不改动任何方块。

## 菜单（sgui 箱子界面）

- **房型**：7×7 生存小屋、带门廊的木屋、双层石木房、小麦田。
- **旋转**：0°、90°、180°、270°。门朝向在预览里标出。
- **位置**：默认放在选区中央，可以用方向键在选区内平移，不能移出选区。
- **地面高度**：默认取选区内最常见的地面高度，可以 ±1 调整，实时显示挖方和填方数量。
- **模式**：「只平建筑地基」（占地加四周 1 格走道）或「平整整个选区」。
- **填坑深度上限**：默认 6 格，超过的坑列为冲突，不偷偷少填。
- **预览图层**：建筑、将挖掉、将填平、受保护、冲突，可以分别开关。
- **材料表**：需要、挖方可得、材料箱已有、缺口。
- **按钮**：确认开工（有冲突时禁用）、取消、撤销选区。
- **施工中**：显示房型、当前版本、状态、阶段、服务端统计的完成数与总数、等待原因和缺料清单。受阻与死亡会显示原因和坐标，越界、放错、现场变化、迟到操作分别计数。暂停、继续、重新比对、取消按当前状态启用。主人可用 `/deskpet plan` 查看状态并打开这一页，无需手持法杖。
- **Boss 栏与提醒**：计划已确认、运行中或暂停时，Boss 栏向主人显示房型、阶段、服务端进度与等待或暂停原因。终态移除 Boss 栏。开工、暂停、完成、失败、取消各在对应事件发生时给主人发一条聊天提醒。
- **施工标记**：受阻点用红色发光标记，死亡点用紫色。主人可以在「施工中」页打开「显示剩余工作」。标记只向主人发送，在离开菜单后清除。
- **历史记录**：主人可查看最近 20 份已结束计划的房型、终态、原因和时间，历史只读。

预览用只发给主人的虚拟 block_display 实体。其他玩家和机器人都看不到，世界里也不会多出实体。改动格子多的时候，只显示变化格的外框，并设显示上限。

## 房型

- 房型是原版结构方块导出的 `.nbt` 文件，旁边配一个 JSON，写入口、门、阶段、脚手架格、建造顺序提示。以后玩家用结构方块存一栋，就多一个房型。
- 7×7 生存小屋移植自 `electron/minecraft-companion-runtime/core/blueprints/starterHouse.js`。
- 首版方块限定为：圆石、木板、竖直原木、玻璃、门、楼梯、下半砖、地面火把、床、箱子、熔炉、工作台。有朝向的方块要先单独测过，才能放进房型。
- 小麦田按 9×9 分块，每块中心放一格水。需要水桶、种子和锄头，由玩家放进材料箱。只负责开垦和播种；长期收割补种属于「长期维护授权」，放到后续阶段。

## 计划编译（只在 Mod 里做）

编译结果是一份明确的操作清单。预览照它渲染，执行方收到的也是同一份，用哈希校验。

```
planId        随机 128 位
revision      重新比对后递增
worldId       Mod 存在存档里的 UUID
dimension     例如 minecraft:overworld
ownerUuid     发起并确认的玩家
botUuid       执行的机器人
selection     水平范围 + 计算出的 minY/maxY
template      房型 id + 版本 + 旋转 + 锚点
groundY, mode, fillDepthLimit
ops[]         { pos, expect, target, kind: clear|cut|fill|build|furnish|scaffold, phase, order }
protected[]   框内受保护、不准动的格子
materials     需要 / 挖方可得 / 箱子已有 / 缺口
supplyChest   材料箱位置
snapshotHash  预览时的范围快照哈希，供诊断和兼容已有计划
expiresAt     预览后 10 分钟
planHash      以上内容规范化后的 sha256
```

`ops` 用调色板加坐标数组编码，传输时分片，每片不超过 32 KB。

### 能动什么（默认允许清单）

- **可以挖**：自然方块。包括土、草方块、石头类、沙、沙砾、黏土、雪；属于自然树的原木和树叶（`persistent=false`）；草、花、蕨等植物。
- **受保护**：木板、玻璃、羊毛、砖、耕地、土径、所有方块实体（箱子、熔炉、漏斗、告示牌、床等）、红石元件、铁轨、`persistent=true` 的树叶，以及不在允许清单里的任何方块。受保护方块挡住建筑时，判「放不下」。拆除以后单独列清单确认。
- **垂直范围**：只挖地面高度及以上的格子；只填地面以下、不超过填坑深度上限的格子。房顶和树顶以上的上限写进计划。

### 首版直接判冲突的情况

- 树跨出选区（除非勾选了「只砍框内」）。
- 要挖的格子挨着水或岩浆。
- 要挖的格子上方的沙子或沙砾柱延伸到选区以外。
- 框外有附着在框内方块上的东西：火把、梯子、藤蔓、告示牌、按钮、拉杆、铁轨、门、地毯、红石线，以及长在顶面的植物。
- 选区放不下房型（不擅自缩小，也不挪出选区）。
- 坑深超过填坑深度上限。

## 授权与防重放

1. 主人点「确认开工」。Mod 检查以下各项：
   - 点按钮的人的 UUID 就是配置的主人，并且是这份计划的发起人；
   - 世界和维度一致；
   - 没有过期；
   - 待施工格和受保护格满足现场规则，再用当前世界检查树木跨界、相邻液体、沙砾柱和附着物；
   - 没有和它重叠的进行中计划；
   - 机器人在线。
2. Mod 生成一次性授权 `{planId, revision, planHash, grantId}`。执行方重新计算计划哈希并回 `accept`。Mod 对当前世界再次做现场和冲突检查，通过后进入运行中。同一个 `grantId` 第二次 `accept` 一律拒绝；执行方也按世界记录用过的 `grantId`。
3. Mod 10 秒收不到执行方心跳，就收回授权，转为「暂停：断线」。重连后必须主人点「继续」。Mod 会把剩余操作和当前世界重新比对，发出下一版授权。执行方自己记得的计划不能拿来继续施工。
4. 等待接单或暂停期间，Mod 只锁这份计划的选区和高度范围。取消、完成或失败后，选区外立即恢复自主挖放，选区内的撤销窗口在 Core 回 `revoke_ack{grantId}` 或满 15 秒时结束。撤销窗口只保留在运行时内存中。
5. Mineflayer 身体通过插件频道 `deskpet:plan` 收授权，只能来自机器人当前连着的服务器。撤销确认随协议版本 2 引入。Mod 身体在进程内直接调用。

## 两层拦截

**第一层：执行方。** 施工期间，所有挖和放都经过一个守卫函数，限制在授权清单里。服务端按当前方块和操作种类判断是否满足 `expect`。
- Mineflayer 版要额外处理这些现有问题：
  - 寻路默认会挖方块（`core/companion.js` 里 `canDig = true`），绕过了 `core/actions.js` 的 `companionProtectBlock`；
  - `core/behaviors/survival.js` 直接调用 `bot.dig`；
  - 夜里挖洞躲藏（`skills.digIn`）、遇险挖掩体（`behaviors/recovery.js`）、脱困、捡掉落物时往下挖，都会在任意位置动方块。
- 施工授权期间，寻路只走现有地形。挖洞、挖掩体、挖路脱困、往下挖捡掉落物、外出打猎和采集均停用。遇险仍可撤退、近战自卫、用背包里的食物和安全药水回血、举盾。追击和撤退以工地为中心，最远 16 格。
- 未获当前施工步骤许可的 `use_item` 只允许在空中使用安全食物、可饮用的安全药水和盾牌。桶、末影珍珠、骨粉、点火物品和会传送的食物继续拦截。对准方块的交互仍按原规则校验。
- 施工默认夜里停工，生存行为仍可运行。受到弓箭伤害时，Core 按服务端报告的来源处理射手，优先在工地范围内反击，无法接近时举盾或撤退。白天遇险时，生存行为可先取得身体控制权。施工重新取得控制权后按服务端回执与现场复核，从中断处继续。
- Core 默认关闭计划接收。启动时加 `--survey-plan-dry-run` 可演练，使用 `--survey-plan-execute` 才会执行。执行模式要等 Mod 校验授权并确认进入运行态才启动施工。授权开始时收回 Core 的其他目标，授权结束后重新决策。

**第二层：Mod 服务端。** 对 DeskPet 机器人玩家（Mineflayer 账号或 Mod 假玩家），授权期间：
- 破坏用 `PlayerBlockBreakEvents.BEFORE` 拦截；
- 物品和方块交互都由服务端守卫检查实际的方块改动，涵盖桶、锄头、斧头、铲子、点火、骨粉和蜜脾；
- 门、活板门、栅栏门、木桶只改变 `open` 属性的操作允许执行。最终比对也忽略这些方块的 `open` 属性。

## 现场变化、缺料与终态

- 确认、接单、续工和执行用同一套现场规则。挖方和清理允许同一份自然方块清单中的变化，例如泥土长成草方块。填方接受空气、可替换的植物和雪层。建筑、家具及脚手架如果预期为空气或可替换物，也按填方规则判断，其余预期状态逐项核对。
- 确认、接单和续工时，用当前世界检查每个待施工格的下一步、已施工的目标格和受保护格。有任何冲突就报第一处的位置和原因。外围的自然变化由世界照常处理，机器人改动范围由服务端授权限制。整片快照留给 `/deskpet debug snapshot` 和独立验收。
- 执行中发现不兼容的方块变化时暂停，并报坐标、预期方块和实际方块。现场恢复后，主人点「继续」可以执行原计划的剩余清单。遇到任意暂停原因，发起计划的主人也可以点「重新比对」，以原房型和版本、旋转、锚点、地面高度、模式、填坑上限、跨界树选项和材料箱重编下一版。
- 比对固定原来的水平和垂直选区。已经符合最终目标的格子保留，缺失的目标和新增的自然障碍按现场重新计算，材料表同步更新。跨界树、相邻流体、越界坠落柱、框外附着和受保护方块重新检查。需要改动框外或受保护格时列为冲突。所有旧操作都完成、最终核对仍不符的计划也可重新比对。
- 比对预览用绿色、品红和浅蓝表示新增、取消和不变的操作，并分别显示数量。主人确认最新预览才发放下一版的一次性授权，与普通预览使用同样的身份、维度、现场、重叠、在线和 10 分钟过期校验。生成新预览会立即作废旧预览。暂停前的授权和已消费授权均不可重放，四类计数跨版本保留。
- 启用随机刻时，已准确放置且低于计划地面标高的填方泥土可以自然长成草方块。准备好的麦田泥土在锄地前长草仍可开垦，已完成的耕地可自然湿润，小麦可自然生长。房型目标、受保护格和动作当下的目标状态仍按授权核对。
- 状态分别记录机器人越界 `violations`、放错状态 `misplacements`、现场变化 `siteChanges` 和迟到操作 `lateAttempts`。执行模式下一次越界即失败。授权位置的指定方块放成了错误状态时，Mod 拒收这次放置并单独计数。Core 换站位或命中点，同一步最多尝试三次，仍无法放对就报告受阻。
- 缺料时，先做能做的阶段，提示缺什么、缺多少。计划保持运行，每 30 秒检查补给。夜间停工也保持运行和心跳，天亮后继续。
- 机器人死亡时，Mod 记录维度和死亡坐标，收回授权，并把计划暂停为 `bot_died`。主人可在施工状态中看到坐标。重生后要由主人重新确认继续，施工材料掉落时留在现场。
- 多出来的原木和土石存回材料箱。箱子满时等待腾出空间。没有安全可达的站位、现场不符等受阻情况才暂停，等主人处理后续工。
- 临时支撑由房型授权。门廊在上部立柱前布置两侧台阶。双层房先搭外侧台阶并安装永久楼梯的起步阶，利用台阶完成楼板、上层墙与屋顶。拆除从高向低。
- 只允许在背包里合成（原木→木板、木棍），不放工作台。
- 计划终态由 Mod 判定，只有这几种：
  - 「完成」：所有清单操作完成，施工目标格和受保护格通过核对，脚手架已拆，机器人越界次数为 0；
  - 「失败（原因）」；
  - 「已取消」；
  - 「已过期」。
- 「已接单」和「运行中」都不算完成。

## 专用服（机器人的世界）

- DeskPet 下载固定版本的服务端和 Mod 文件，并校验 sha256。
- `server-ip=127.0.0.1`。过渡期 Mineflayer 机器人还要进服，所以先开离线模式，只允许本机连接。朋友加入之前，必须完成 Mod 身体迁移，并改成 `online-mode=true` 加白名单。
- `pause-when-empty-seconds=0`：玩家下线后世界继续运行。
- 内存 `-Xmx3G` 左右，和本地大模型同时跑时要留意。
- 进程崩溃自动重启，世界备份保留 3 份。
- 玩家下线期间，模型调用要有上限（例如只做死亡复盘），不能无限制地花额度。
- 默认新建世界。导入已有单人存档作为可选项。

- 判定以 Mod 调试命令导出的服务端快照为准（选区、外围 8 格、上方空间），加上 Mod 记录的计划终态。界面上显示「已接单」不算通过。

### 身体实验的考题

1. 假玩家：参考 Carpet 的 `/player` 做法，是一个真正的 ServerPlayerEntity，出现在玩家列表里，按每个世界固定的 UUID 保存背包，服务器重启后自动回来。移动靠模拟操作输入（前进、跳、潜行、视角），走原版玩家物理。不能瞬移，不能飞，不能穿墙。
2. 挖和放都走原版交互路径（`ServerPlayerInteractionManager` 的挖掘进度、带命中点的 `interactBlock`），遵守挖掘时间、4.5 格触及距离和物品消耗。不能用 `setBlockState` 走捷径。
3. 寻路：在服务器线程上分片执行，每刻不超过 5 ms，或者在只读快照上异步计算。在平原、森林、丘陵各取一组固定种子和目标，100 格内 20 个目标的成功率不低于 Mineflayer 版在同一组目标上的成功率。
4. 施工：执行 M2 的授权，在 4 个方向上完成整地和 7×7 小屋，通过 M3 的验收。
5. 战斗：竞技场里拿石剑打死一只僵尸。
6. 性能：平均 MSPT 增加不超过 2 ms，没有超过 50 ms 的服务器线程卡顿。
