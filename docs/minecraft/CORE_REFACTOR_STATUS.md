# Minecraft Core 重构：进度总结（2026-11-24 暂停）

主人决定暂时搁置 Core 的改进。本文记下停在哪里、哪些已经可靠、哪些还没解决，以及恢复时从哪里接着做。设计和每一轮的规则见同目录的 `CORE_REFACTOR_DESIGN.md`。

## 一句话现状

- **底层可靠：**动作、保命反射、过夜、救援、失败账本、doctor，加上服务端真相核对，现在基本可靠。
- **判断层是瓶颈：**选下一件事、换办法、选址、搬迁，规则越补越多，自然跑的里程碑一直没稳定达标。
- **下一步：**已经计划好用低频调用的模型来替换判断层，先做 A/B 实验验证。实验还没开始。

## 已经可靠的部分

- **统一的动作结果：**`{ok, kind, reason, facts}`。失败的 `facts` 写明目标、缺什么、试过什么、离家多远，每条不超过 1 KB，将来交给模型读也能看懂。
- **按优先级分带：**保命（rescue 130）> 防卫 > 过夜 > 任务。救援之间不会互相抢身体。
- **掩蔽状态每次按身边方块和服务端坐标重新算，**不用锁存的标志。拆掉一块盖板时立刻变成 false；家里屋盖被破坏时会重新找掩体。
- **出坑和出水是一条梯子：**有没有镐都能挖。「到了」和「已出坑」用同一个定义（坑外能站的一格）；同样的尝试不重复。
- **就地掩体最少只要 1 块料，**跳在空中时被夜间行为接手也能完成。
- **逃跑按结果核对：**距离真的拉开、2 秒内没再挨打，才算成功；跑不掉就堵道、垫高或者围起来。
- **采种子一次拔到够为止**（上限 24 株、90 秒）。
- **定址前的探索原点跟着 Bot 走；**在范围外先走回来再搜索。
- **定点夹具只检查物理结果和服务端事实，**不检查判断层的记录。换了 director 以后，定点照样能用。
- **单测：**Core 369/369。R4.3 那一轮另跑过 App 的 Minecraft Vitest 145/145、TypeScript 类型检查和 Mod JUnit 25/25，都通过。

## 没解决的问题

1. **判断层（主要问题）：**
   - 卡片打分、`stale`、迟滞和退避；
   - 前置条件，比如九格播种；
   - 搬迁时放宽的选址条件；
   - 首夜前选不到能尽快住进去的房址。
2. 种子 2（沙漠和水多的地形）90 分钟内一直没住进房子。
3. R4.3.1 修订提交还缺：
   - 28 个定点在同一提交上的正式复跑（修订时只在隔离副本里复验）；
   - 三组正式自然跑。
4. Mod JUnit 依赖本机 Loom 缓存，要用宽松校验才能离线运行。

## 恢复时从哪里接着做

1. 用 `d3eecd3` 跑完 R4.3.1 的定点和三组自然跑，作为 A 组（手写 director）基线。
2. 做模型 director A/B 实验：
   - 加开关 `CORE_DIRECTOR=llm`。打开后，由模型从固定的技能菜单里选下一步，参数经过校验；
   - 协议沿用现有的 `adaptation_help`：Core 发 `director_request`，由 App 或测试程序调用模型，再回 `director_reply`。Core 里不放 key，也不发网络请求；
   - 保命、过夜、安全规则、失败账本、doctor 都留在本地；
   - 采用标准事先定好：
     - 里程碑不差于 A 组；
     - 安全零计数为 0；
     - 每小时调用不超过 120 次，回复延迟 p95 不超过 15 秒；
     - 删除试验净减至少 21,500 token。
3. 如果采用，就删掉手写的判断层（R5）。如果不采用，再考虑冻结下界和末地部分来控制体量。

不选 computer use（截图加鼠标键盘）的原因：
- Minecraft 需要零点几秒的实时反应；
- 每一步都带截图，token 成本太高；
- 画面不如服务端坐标准确。
